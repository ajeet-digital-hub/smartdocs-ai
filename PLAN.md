# Family Guardian - Phase 2.5+ Architecture Plan

## Current State Analysis

Phase 1 provides:
- Family/Child management with embedded device subdocuments
- WebsitePolicy for domain-based blocking with schedule blocks and daily limits
- Schedule model with time-based rules and websiteRules
- Unlock requests for websites (approved_once, approved_10min, approved_30min)
- Reward goals for study-based screen time rewards
- Activity logging for audit trail
- Basic pairing code generation (text-only, 30-min expiry, stored on Family doc)

## Key Architecture Problems to Solve

1. **No standalone Device model** - Devices embedded in Child, can't track independently
2. **No AppPolicy model** - Apps mapped to WebsitePolicy by domain (no package name, no installed status)
3. **No device synchronization API** - No way for mobile app to fetch policies, report status
4. **No device authentication** - Pairing code is the only auth, no device tokens
5. **No installed app detection** - Dashboard can't distinguish "Available Policy" vs "Detected on Device"
6. **No app usage tracking** - No mechanism to report actual usage from device
7. **No mobile app** - Android/iOS apps don't exist yet

### 2. New API Routes

#### `/api/family-guardian/pair-device` (ENHANCED)
- Generate pairing code with QR data URL
- Return: `{ pairingCode, qrDataUrl (base64 PNG), expiresAt, childId }`
- Code: 8-char alphanumeric, 15-min expiry (reduced from 30min)
- Single-use, cleared after successful pair
- Log: `device_pair_initiated`

#### `/api/family-guardian/device-auth` (NEW - unauthenticated)
- Device calls this to authenticate after scanning code
- Accepts: `{ pairingCode, deviceId, deviceName, platform, fcmToken?, publicKey? }`
- Creates Device document with secure deviceToken
- Returns: `{ deviceToken, childId, familyId }`
- Device stores deviceToken locally for all future API calls

#### `/api/family-guardian/devices` (ENHANCED)
- GET: List devices (with optional childId filter)
- DELETE: Revoke device (remove device + clear deviceToken)
- PATCH: Update device status

#### `/api/family-guardian/sync-policies` (NEW - deviceToken auth)
- GET (device-authenticated): Returns all AppPolicy + WebsitePolicy for this child
- Includes policyVersion for delta sync
- Response: `{ appPolicies, websitePolicies, schedules, policyVersion }`

#### `/api/family-guardian/device-heartbeat` (NEW - deviceToken auth)
- POST: Device reports status, installed apps, battery, foreground app
- Updates Device.lastSeen, Device.status, Device.installedApps
- Returns: `{ policyUpdatesRequired: boolean, pendingUnlockRequests: number }`

#### `/api/family-guardian/report-usage` (NEW - deviceToken auth)
- POST: Device reports app usage (where platform allows)
- Body: `{ usage: [{ packageName, foregroundTime, date }] }`
- Stores in ActivityLog

#### `/api/family-guardian/temp-unlock` (NEW - deviceToken auth)
- POST: Child requests temporary unlock from device
- Creates UnlockRequest (reusing existing model with appId/appPackage)
- Returns: `{ requestId, status: "pending" }`

#### `/api/family-guardian/revoke-device` (NEW - session auth)
- POST: Parent revokes a device
- Clears deviceToken, sets status to offline
- Logs: `device_pair_revoked`

### Core Android Features

#### 1. Device Pairing Flow
1. Child opens app → sees QR scanner / code entry
2. Parent generates code in web dashboard
3. Child scans QR / enters code
4. App calls `POST /api/auth-device` with code + device info
5. Backend creates Device record, returns deviceToken
6. App stores token securely (EncryptedSharedPreferences)
7. Device shows as "Online" in parent dashboard

#### 2. Policy Sync (Background + Foreground)
- On app launch: Fetch all policies
- WorkManager periodic sync: Every 5 minutes
- On policy change notification (FCM): Immediate sync
- Store locally in Room for offline access
- Apply restrictions based on current time + schedule

#### 3. Installed App Detection
- Query PackageManager for installed packages
- Filter against known app catalog packages
- Report detected apps to backend via heartbeat
- **Limitations**: 
  - QUERY_ALL_PACKAGES may be restricted by Google Play
  - Cannot detect apps installed in work profile
  - iOS does not allow listing installed apps at all

#### 4. Screen Time Tracking
- UsageStatsManager.queryUsageStats() (Android 9+)
- Requires PACKAGE_USAGE_STATS permission (user must grant)
- Track: total screen time, per-app foreground time
- Report to backend daily or on significant changes
- **Limitation**: Usage stats reset on device reboot for some manufacturers

#### 5. App Blocking / Restriction
- **Option A (Recommended)**: Device Policy Controller (DPC)
  - Set as Device Admin → can lock task, disable apps
  - Requires user to activate admin
  - Not available on all devices (Samsung Knox, etc.)
  
- **Option B (Fallback)**: AccessibilityService
  - Can detect current app and show overlay
  - Cannot actually block app launch
  - Google Play restricts AccessibilityService use
  
- **Option C (Simplest)**: Self-regulation with lock screen overlay
  - Detect policy violation → show full-screen overlay
  - Child can dismiss but usage is logged
  - Parent sees violations in dashboard

**Recommendation**: Implement Option C as primary (works on all devices),
with Option A as enhancement for devices that support Device Admin.

#### 6. Lock Screen Overlay
- Shown when:
  - Scheduled restricted time (study, sleep)
  - Daily limit exceeded for app category
  - Child requests unlock (waiting for parent approval)
- Shows:
  - "Study Time - You have 15 minutes remaining"
  - "App blocked - Ask parent for more time"
  - "Sleep mode activated - Good night!"
- Uses SYSTEM_ALERT_WINDOW permission
- Child can: Request unlock, View remaining time, See schedule

#### 7. Unlock Request Flow (from Android)
1. Child taps "Request More Time" on lock screen
2. App shows: pick app, reason, emergency option
3. POST to `/api/temp-unlock`
4. Parent notified via push + dashboard notification
5. Parent approves/denies → FCM push to device
6. App receives approval → temporarily unlocks

## PHASE 4 — iOS CHILD APP ARCHITECTURE

### Apple Platform Constraints
- **Cannot list installed apps** - iOS has no API for this
- **Cannot block apps programmatically** - Not possible without MDM
- **Cannot read screen time data** - Family Controls API is read-only for third parties
- **Can use Screen Time API** - Only to create restrictions (parent must approve)

### Technology Stack
- **Language**: Swift 5.9+
- **UI Framework**: SwiftUI
- **Architecture**: MVVM + Combine
- **Networking**: URLSession + async/await
- **Local Storage**: CoreData / SwiftData
- **Auth**: Keychain Services
- **Push**: Apple Push Notification Service (APNs) via FCM
- **Background Tasks**: BGTaskScheduler

### iOS Permissions

### ⚠️ Remaining Limitations

1. **No cross-platform app blocking** - Each platform requires native implementation
2. **Apple restrictions** - iOS cannot block apps or track usage without Screen Time API (parent-controlled)
3. **Android fragmentation** - Device admin capabilities vary by manufacturer
4. **No browser extension yet** - Website blocking requires browser extension for enforcement
5. **No real-time sync** - Heartbeat is periodic (2-5 min), not real-time
6. **No end-to-end encryption** - Policy data sent in plaintext (HTTPS only)
7. **No multi-device conflict resolution** - If two devices have same app, policies apply individually
8. **No geofencing** - No location-based restrictions
9. **No content filtering** - Can only block entire apps, not specific content
10. **No analytics export** - No CSV/PDF export of usage data
